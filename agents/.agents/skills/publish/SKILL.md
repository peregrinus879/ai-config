# Publish

Run this before presenting any push, release, pull request, or other publication as ready, including when no new commit is needed. H runs the push command; the skill verifies the result afterwards. The `publish-bind` and `publish-verify` scripts carry the procedure.

1. Run `~/.agents/skills/publish/scripts/publish-bind [<ref>]`, default `HEAD`, or add `--remote <remote> --branch <branch>` for H's named destination. It binds a single resolved push endpoint, branch, reviewed commit, tracking baseline (assumed without a fetch), and relevant configuration to an immutable `binding-id`. A non-descendant is a destructive request for H's separate ruling. Multiple destinations, embedded endpoint credentials, unsupported helpers/options, and absent first-publication baselines refuse; never bypass these or display credential-bearing values. First publication or audience expansion needs explicit complete-history review and an appropriate separately reviewed procedure, not an invented baseline.
2. Review every new commit and its metadata, including transient content removed before the tip. The script scans explicit per-parent merge patches, complete newly reachable objects and tree paths, and the flat diff. Actual sensitive/identity findings block readiness. A partial scan binds exact unscanned object IDs, sizes, reasons and historical tree/path locations; show metadata only and require H's inspection before publication, never claim a complete scan. Review the bound effective pre-push hook and intended behavior, including symlink target/content digest; normal hooks remain enabled. A ready receipt means recorded scope, not completed human review. The audience is H's declared audience, else world-readable.
3. Run the repository's gates on the reviewed contents, using only the commit skill's conservative same-workstream evidence reuse rules. `commit-apply` provenance never substitutes for gates. Keep exact final-pair verification for coordinated twin repositories: a green check against an arbitrary earlier peer does not validate the pair being published.
4. Account for anything else the operation would publish: release or pull request metadata, bodies, and assets.
5. Present a compact packet with repository/`binding-id`, bound destination/base/reviewed IDs, commit list, gate/scan/privacy and hook review, required object inspection, and the script's generated command verbatim. Preserve its `--check ID` preflight and explicit record-root environment, configured remote name, pinned one-branch refspec, tag/submodule suppression, normal hook enforcement, and exact-base lease. The named remote preserves normal tracking updates and hook arguments; preflight checks its bound endpoint/configuration, but the separate check and push are not atomic against adversarial changes. If configuration, scope or audience changes, rebind and review. Join complete per-repository commands with `&&` in commit order, show each command for review and the combined line once, and let H run it. Before the selector, pass that line to `~/.agents/skills/publish/scripts/publish-clip` and repeat its `clipboard: <tool|none>` result. Use `Pushed, verify and resume` first and `Pushed, verify and pause` second; repeat the combined command on its own line in the question so a hidden packet cannot obscure it. Free text is discussion, not confirmation: answer, re-present command/selector. Only a selected option starts verification; no pasted output is required.
6. Run `~/.agents/skills/publish/scripts/publish-verify ID` for each exact binding, in order and with its record root. It checks bound configuration again, observes the bound push endpoint through read-only `ls-remote`, reports local tracking separately, and runs `make verify-published REV=<id>` or `npm run verify-published -- <id>` only where defined. Query relevant hosted CI separately through read-only `gh` checks, reporting pending/failed/unknown honestly; for twin changes verify the exact final committed pair and identify any hosted pair run still needed. Remote equality is point-in-time evidence, not proof who pushed; stale local tracking or a later remote mismatch does not establish that H's push never landed. An offline/error result is unknown, not failure-to-push. Report per-repository observations and stop on unexpected state; do not blindly retry stale leases or mutate tracking to make checks pass. Confirm remaining actions with H and rebind changed bases. Finish cleanup and report all repositories together; `resume` continues remaining authorized work, `pause` stops for discussion.

Remote observation needs command-network access. In Codex's network-disabled profile, ask H to run the exact verifier ID from the repository with the same record root, or use an already authorized tool context with network access; do not weaken the sandbox. Opaque/custom SSH shell expressions can also leave verification unavailable. Report that known limitation as unknown and arrange verification deliberately, not an endless rebind/retry loop. Rebinding from a different context requires fresh review if bound configuration or executable inputs differ.
