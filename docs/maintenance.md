### SSH Verifier Access

Deferred by H on 2026-09-08 pending an explicit authentication/access decision. In the inspected Omarchy OpenCode context, `SSH_AUTH_SOCK` was absent, the bounded agent query was unavailable, and the installed OpenSSH user socket was disabled. Recheck the current provider and launch environment before proposing setup; these observations do not establish every possible agent configuration. Hosted CI and local tracking do not replace the still-unverified bound SSH observation.

> **Warning: Authentication Is Not Read-Only.** An unlocked agent supplies signatures under the loaded key's server-side permissions and agent restrictions. An account key may permit pushes as well as reads. Commit/push approval rules remain mandatory, but are not a cryptographic read-only restriction on that key.

> **Warning: The Socket Is A Capability.** Processes able to access the socket, including other same-user processes or root, can request signing. Passing its path only to one command is not strong isolation from other same-user software. Ordinary agent use does not send the private key to the model or GitHub or remove the key file's passphrase, but it makes authentication available without repeatedly entering that passphrase.

> **Warning: Persistence And Lifetime Differ.** Enabling a user socket persists across logins; exporting `SSH_AUTH_SOCK` affects only that shell and future children, not an already-running tmux/OpenCode process. Loaded keys remain usable until removed, expired or the agent stops. Do not promise logout always clears them. Bounded lifetimes reduce exposure; per-use confirmation can prevent unattended verification.

> **Warning: No Implicit Sharing Or Bypass.** Agent setup does not itself configure forwarding or supply credentials to GitHub Actions. Any forwarding or socket sharing needs separate review. Do not weaken `BatchMode`, host-key checks or native permissions, silently substitute an observation endpoint, retry old push leases, or mark a binding verified from CI/tracking alone.

Discuss these alternatives before acting:

- A single user-scoped agent, only the intended key, a bounded lifetime and optional confirmation: convenient authenticated Git use, with the signing-access tradeoff above. H loads keys; any persistent session wiring needs explicit target/approval and must preserve another valid agent handle.
- H-controlled, temporary authenticated verification: no persistent agent setup for the assistant workflow, but more manual work and the same socket-access risk during the agent's lifetime.
- Explicitly reviewed credential-free verification for public repositories, or narrowly scoped credentials where authentication is necessary: potentially less authority, but additional verifier/credential-management design. It must preserve the bound-repository and transport evidence contract rather than masquerade as an observation over an untested SSH path.

Owner: EyrAgents for verification policy and evidence; the applicable host repository for any later approved startup integration. No service activation, key loading, credential read or authentication/startup change is approved by this deferral. Revisit on H's authentication decision or a relevant transport/launch-policy change.
